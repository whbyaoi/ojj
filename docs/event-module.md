# 事件模块设计（v0.1）

## 1. 目标与状态

事件模块接收不同生产者投递的事件，以广播订阅方式交给消费者处理，并保留事件与投递记录，便于后台查看。

本文独立细化原设计草案中的事件部分；不要求同时实现 Agent、情绪、记忆或 IM 接入。

- **已确认**：文本正文与结构化数据并存；广播订阅；稳定订阅身份；按入库顺序投递；成功确认；失败有限重试；允许重复投递；消费者避免重复副作用；慢消费者不阻塞其他消费者及生产者。
- **契约解释**：接收成功表示系统接管后续处理责任，不表示所有订阅者已经处理成功。该解释用于协调“后续处理”与“不阻塞”，仍需确认。
- **建议默认值**：本文标为建议的存储、字段、历史订阅、顺序与容量策略，作为首版实现依据候选，不代表已经确认。

## 2. 模块职责

事件模块负责入口校验、持久化、订阅匹配、广播投递、处理确认、有限重试和查询记录。

事件模块不解释正文、不生成摘要、不决定回复、不修改情绪或记忆，也不调用 LLM。批次汇总、固定延迟和 Agent 串行循环属于消费者侧调度。

生产者负责把输入转换为事件，并保证其格式符合协议；消费者负责理解和使用内容。格式合格不等于内容真实或可信。

## 3. 事件模型

### 3.1 文本正文

正文统一使用文本，允许生产者按用途组织描述。例如：

```text
当前时间 2026-11-09 10:00:00+08:00，这是一次心跳事件，请自由地遵从你的内心，做出你想做的事情，当然什么都不做最好。
```

```text
当前时间 2026-11-09 10:01:00+08:00，接收到来自小明（id=123456）的私聊消息：今天过得怎么样？
```

事件系统只检查正文类型和大小，不检查语义有效性。消费者不得通过解析正文来恢复路由、权限或来源身份。

### 3.2 结构化外壳（建议字段）

| 字段 | 必需 | 责任与含义 |
|---|---|---|
| event_id | 是 | 系统分配的内部唯一编号，不是平台消息编号 |
| sequence | 是 | 系统分配的持久化入库序号，用于投递排序 |
| producer_id | 是 | 由接入层绑定的稳定生产者身份 |
| event_type | 是 | 生产者声明的事件类型，如 heartbeat、im.message |
| occurred_at | 是 | 生产者提供的发生时间，包含时区 |
| received_at | 是 | 系统记录的接收时间，不用于替代发生时间 |
| content | 是 | 事件实际文本正文 |
| schema_version | 是 | 外壳协议版本，首版固定为 1 |
| source | 否 | 结构化来源；IM 事件需包含平台、接入账号、会话类型、会话编号、发送者编号及原始消息编号 |
| deduplication_key | 否 | 生产者重投时保持不变的去重键，与生产者身份联合唯一 |
| correlation_id | 否 | 关联后台任务或业务流程的编号 |
| causation_event_id | 否 | 直接引发此事件的上游事件编号 |

不同类型可要求不同来源字段；心跳不需要伪造发送者或会话。路由和来源识别始终以外壳为准；若生产者或消费者发现正文与外壳冲突，应记录异常，事件模块本身不进行语义比对。

入口身份可信不代表正文可信：IM 生产者传来的用户文本仍是外部输入。用户不能通过正文声明自己是系统或心跳生产者。

事件入库后保持不可变。投递状态单独记录，不在事件上设置全局“已处理”状态。

## 4. 接收与后续处理契约

### 4.1 建议采用的接收语义

1. 生产者提交事件，入口校验身份、必填字段、类型、正文长度和容量限制。
2. 在事务中写入事件及当前匹配的订阅投递记录，然后返回事件编号和接收成功。
3. 各订阅者异步处理；处理结果可以通过事件编号查询，不占用生产者提交调用。
4. 入库或校验失败时明确拒绝，不返回成功；调用结果不确定时，生产者可携带原去重键重投。

接收成功承诺事件进入后续处理流程，直到对应投递成功或进入可查询的最终失败状态；不承诺业务一定成功。去重命中返回既有事件编号，不重新生成广播记录；同一去重键提交不同内容时明确报冲突。

**待确认的措辞边界**：如果“接收成功”必须表示业务已经处理完成，应另外提供异步处理完成通知，并定义是哪些订阅者完成才算成功，而不是让普通提交等待所有消费者。

### 4.2 没有匹配订阅者

建议仍保存事件，并在接收结果及后台查询中明确显示“匹配订阅者数量为零”，不能显示成已被消费。后续新增订阅默认不自动接收这条历史事件。

## 5. 广播订阅

每个订阅使用稳定身份，配置事件类型或生产者等结构化过滤条件。首版不提供正文语义过滤。

同一事件匹配三个订阅，就产生三份独立投递记录，各自确认和重试。一个订阅完成不影响另外两个；一个订阅失败不撤销其他订阅已经完成的副作用。

建议新订阅从创建后的事件开始，重启恢复原订阅的未完成投递。历史重放必须显式指定范围，且可能重新触发外部副作用；不作为首版必需功能。

建议订阅身份与过滤条件持久化。重新绑定相同身份时不得静默改变过滤条件；变更只影响之后入库的事件，不改写已有投递记录。

临时断开或暂停订阅不等于删除，积压继续保留；停用并取消积压必须显式执行并留痕。首版每个订阅仅允许一个活动处理实例，不实现同订阅多实例竞争消费。

## 6. 顺序、确认与重试

### 6.1 顺序边界

按系统入库序号而非生产者时间排序；不同来源时钟可能不同，系统不保证真实世界发生顺序。

建议每个订阅串行处理：前一条完成或最终失败后，再投递下一条。失败等待重试期间暂停该订阅的后续事件，以维持首次处理及重试的串行顺序。不同订阅之间没有完成顺序保证。

因此，“不阻塞”指消费者之间和消费对生产者的隔离，不代表同一订阅内后续事件可以越过失败事件。若以后需要越过，必须明确放宽顺序保证。

### 6.2 独立投递记录（建议字段）

每份记录保存事件编号、订阅身份、状态、尝试次数、下次重试时间、最近错误、处理开始时间及完成时间；事件编号与订阅身份联合唯一。

状态流转：待处理 → 处理中 → 成功；失败或确认超时后进入等待重试，再回到处理中；尝试耗尽进入最终失败并保留错误记录。只有旧回调真正退出后，才启动该订阅的下一次调用（包括重试和后续事件）。

确认必须对应本次投递尝试，过期尝试的迟到确认不能覆盖新尝试状态。Go 回调无法强制终止：不响应取消且永不退出的回调会永久阻塞本订阅，即使投递已经最终失败，也不越过旧回调。其他订阅仍独立运行。关闭存储不等待这类回调；关闭后重新打开存储可能与旧回调的外部副作用重叠，消费者必须幂等并响应取消，强隔离需使用外部进程。

### 6.3 交付保证与恢复

已确认：允许重复投递，不保证严格只处理一次。有限重试也不保证最终业务成功；最终失败必须可见，不能静默丢弃。

消费者只有在完成自己的业务责任后才确认；若消费者只是转交到下游队列，必须先可靠保存到下游再确认，而不是放入临时内存后就确认。

建议失败采用有上限的退避重试，次数、超时和间隔由配置决定。单进程重启后，将未确认的处理中记录恢复为可重试；重试次数跨重启保留，成功记录不自动重投。

消费者以稳定事件编号和订阅身份识别重复。内部状态修改应与幂等记录保持事务一致；外部 IM 已发送但本地未记成功时仍可能重复发送，事件模块不能独自解决这一问题。

## 7. 非阻塞与容量边界

发布过程不执行消费者逻辑，也不等待消费者确认；但仍需等待有界的校验和落盘，不承诺零等待或无限吞吐。

每个订阅独立调度，异常不得传播到其他订阅。消费者不得在共享调度线程执行阻塞任务；需要时采用工作线程或进程，并限制并发和处理时长。

建议持久化记录为事实来源，内存唤醒仅作加速；丢失一次唤醒通知不能造成事件永久不被投递。

必须配置正文大小、订阅积压、存储容量与记录保留期限。建议首版达到硬限制时明确拒收，不静默覆盖未完成事件；接收事务失败时不产生部分广播。

慢订阅短期不阻塞其他订阅，但长期积压仍会消耗共享容量。严格无限隔离不在首版承诺范围；容量不足可能导致入口拒收，需要后台可见并支持显式停用问题订阅。

心跳合并、过期消息不回复等属于生产者或消费者策略，通用事件模块不通过正文推断。消费者决定忽略事件时仍应确认并记录原因。

## 8. 持久化与后台查询

首版实现使用单进程 SQLite（WAL、synchronous=FULL），持久保存事件、订阅配置及独立投递记录，不引入外部消息中间件。仅支持本地普通文件，父目录须已存在；以规范路径旁的 `.lock` 文件排他锁定所有权，锁文件保留且运行期间不得删除或替换。符号链接会规范化，不支持通过硬链接别名访问同一数据库，也不得复制或替换运行中的数据库及其伴随文件。

容量限制按事件、订阅及投递记录进行逻辑记账，不是数据库文件或磁盘配额；清理不保证物理文件立即缩小。仅当事件及全部投递终态均超过保留期才清理，未完成投递保留；去重键随事件清理失效。稳定订阅身份、过滤器及永久停用记录持续保留，首版不提供过滤器修改接口。

查询至少支持按事件编号、时间范围、生产者、类型和订阅投递状态筛选；能查看正文、匹配订阅、各订阅尝试次数和最近错误。聚合完成状态只能用于展示，不替代每份投递记录。

本阶段提供查询能力即可，不要求实现后台页面。消息正文可能包含隐私，查询需受访问控制；普通运行日志避免重复输出全文，保留期限和清理方式应显式配置。

## 9. 首版验收与待确认项

验收场景：两个订阅各自收到相同事件；其中一个失败不影响另一个；去重重投不新增事件；消费顺序稳定；确认后不自动重投；崩溃恢复未确认记录；重试耗尽可查询；容量不足明确拒收；无订阅事件可查询。

还应验证迟到确认不能覆盖新尝试、去重键内容冲突被拒绝，以及生产者提交耗时不随消费者业务耗时增长。

实现前确认：接收成功的解释、上述建议字段、新订阅起点、失败时是否坚持订阅内顺序、超时与重试参数、容量与保留策略，以及实现语言。正文模板由各生产者自行维护，不作为事件模块的固定协议。
